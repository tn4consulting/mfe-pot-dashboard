# mfe-pot-dashboard

## What this is

The **MSCA-D** frontend for the mfe-pot Government of Canada MFE proof-of-technology: 360° cross-benefit overview (eligible benefits, active applications, "my tasks"), payment history, correspondence, and "tell us once" profile maintenance. Federated as a remote into `mfe-pot-shell`; also exposes a standalone payment-history widget embedded directly into `mfe-pot-employment-life-events` (the one proven cross-remote widget-composition case in this architecture).

**This repo doesn't carry its own architecture doc.** Full rationale — bilingual/WCAG/GCDS requirements, the Native Federation setup, why apps are thin and libs hold the logic, the federation-sharing policy, security model, i18n mechanism, the BFF partial-failure pattern, hosting/Helm pattern, and every non-obvious gotcha behind the code in this repo — lives in **`../mfe-pot-platform/CLAUDE.md`**. Read it before making any architectural change here; this file only covers what's specific to this repo. See `../CLAUDE.md` (the `mfe-pot` meta repo) for the full 6-repo map.

## What's in this repo

- `apps/dashboard` — the frontend, federated on port `4201` in local dev.
- `apps/dashboard-bff` — dashboard's dedicated BFF (port `3004`), which composes MSCA-D's cross-benefit overview by calling `job-bank-bff` and `employment-insurance-bff` over real HTTP (`src/config.ts`'s `JOB_BANK_BFF_URL`/`EMPLOYMENT_INSURANCE_BFF_URL`) — never by importing another domain's in-memory state — plus its own local payments/correspondence data (`src/data.ts`, the same in-memory-stub pattern `job-bank-bff`/`employment-insurance-bff` use for their own domains).
- `libs/feature-payment-history` — the payment-history widget, exposed via federation as `./PaymentHistoryWidget` (`federation.config.mjs`) so `employment-life-events` can embed it directly. `libs/data-access` — dashboard's `BenefitAggregationApiClient`.
- `charts/dashboard` — deploys the frontend+BFF pair as one Helm release, depending on both platform-repo library charts (`mfe-frontend-lib`, `mfe-backend-lib`).

Depends on published packages from GitHub Packages: `@tn4consulting/shared-auth`, `shared-content-client`, `shared-federation-config`, `shared-i18n`, `shared-runtime-config` (pinned in `package.json`; keep in sync with `platform-versions.json` in `mfe-pot-platform`).

## Repo-specific things worth knowing

- **`dashboard-bff` is architecturally different from the other two extracted BFFs**: it's a fan-out aggregator for `activeApplications`/`jobApplications`/`eiReportingStatus`, not a self-contained leaf service for those tiles. `overview.ts`'s partial-failure contract (`UpstreamResult<T>` — `{status:'ok', data}` vs `{status:'unavailable'}`) means a slow/failed upstream degrades only its own tile, never the whole response — verified live on `kind` with job-bank/employment-insurance deployed (their tiles returned real data) and separately with one of them killed (only its own tile degraded). `payments`/`correspondence` are served from `dashboard-bff`'s own local `data.ts` (no upstream, so always `'ok'`) — see "Known, accepted tradeoff" note below.
- **In the Helm chart, `JOB_BANK_BFF_URL`/`EMPLOYMENT_INSURANCE_BFF_URL` point at sibling/platform-repo in-cluster Kubernetes Service DNS** (`job-bank-bff.default.svc.cluster.local`, etc.) — genuine cross-Helm-release, cross-repo service-to-service traffic, not routed back out through Ingress. `dashboardBffBaseUrl` on the frontend side is the opposite: `/api`, a same-origin Ingress path rule, since that call is browser-to-server.
- **`strapiBaseUrl` now points at `mfe-pot-platform`'s real `charts/strapi` Ingress hostname** (`http://cms.mfe-pot.local`, browser-to-server, not in-cluster Service DNS — confirmed live).
- **Payments/correspondence used to be served by a separate `client-profile-service` (`mfe-pot-platform`) — removed.** That service had no Helm chart, so its one caller (`dashboard-bff`) 502'd in any real deployment. Its data now lives directly in `dashboard-bff`'s own `src/data.ts`, the same in-memory-stub pattern `job-bank-bff`/`employment-insurance-bff` already use — `HttpPaymentHistoryApiClient` still calls `dashboard-bff`'s `/api/payments`, unchanged, just no longer a proxy. **Known, accepted tradeoff**: `client-profile-service` existed specifically so this data was one shared source across all three domain BFFs (its own doc comment said so); folding it into `dashboard-bff` makes it dashboard-only, narrowing the not-yet-built "tell us once" cross-service demo beat (`../TODO.md`) — flagged there as needing a redesign, not silently dropped.
- **`federation.config.mjs`'s `exposes` map has a third entry beyond the usual `./Component`**: `./PaymentHistoryWidget` (from `libs/feature-payment-history`) and `./RemoteProviders` (dashboard's own DI providers, which `employment-life-events` also loads alongside the widget so it runs in the right environment injector — see the platform repo's CLAUDE.md, "The cross-remote payment-history widget needed the same component+providers pairing"). If you ever move or rename this lib, this is the file that breaks first (`FsPath ... does not exist`), not `tsconfig.app.json`.
- **Known functional gap** (tracked in `../TODO.md`, the root `mfe-pot` meta repo's cross-repo TODO — not a bug to "fix" here without asking): the payment-history widget still renders static English mock data — none of it wired to Transloco/locale-aware formatting yet.
- **CI** (`.github/workflows/ci.yml`): lint/test/build (including `dashboard-bff`'s separately-run `eslint:lint` target), then builds both images, spins up an ephemeral `kind` cluster, `helm install`s this chart, and curls the Ingress-routed hostname to confirm it serves. The `/api/overview` smoke check deliberately omits the `sub` query param (asserts a 400, not a 404) rather than exercising the real fan-out, since this workflow doesn't also deploy job-bank/employment-insurance. See `README.md` for local install/serve/build/Docker/Helm instructions.
