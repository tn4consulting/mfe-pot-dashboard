# mfe-pot-dashboard

## What this is

The **MSCA-D** frontend for the mfe-pot Government of Canada MFE proof-of-technology: 360° cross-benefit overview (eligible benefits, active applications, "my tasks"), payment history, correspondence, and "tell us once" profile maintenance. Federated as a remote into `mfe-pot-shell`; also exposes a standalone payment-history widget embedded directly into `mfe-pot-employment-life-events`, and embeds job-bank's job-applications widget and employment-insurance's EI-reporting-status widget in its own overview (host-mediated via the shell — see the platform repo's CLAUDE.md "Federation" section) — the one app in the family that's both a widget *source* and a widget *consumer*.

**This repo doesn't carry its own architecture doc.** Full rationale — bilingual/WCAG/GCDS requirements, the Native Federation setup, why apps are thin and libs hold the logic, the federation-sharing policy, security model, i18n mechanism, the BFF pattern, hosting/Helm pattern, and every non-obvious gotcha behind the code in this repo — lives in **`../mfe-pot-platform/CLAUDE.md`**. Read it before working on anything architectural here; this file only covers what's specific to this repo. See `../CLAUDE.md` (the `mfe-pot` meta repo) for the full 6-repo map.

## What's in this repo

- `apps/dashboard` — the frontend, federated on port `4201` in local dev. `apps/dashboard/src/app/*.tsx` holds every component directly (`App.tsx`, `Overview.tsx`, `PaymentHistory.tsx`, and the smaller `WhatsNewList.tsx`/`NeedsAttentionList.tsx`/`TasksList.tsx`/`ConsiderThisList.tsx`) — no separate `libs/<name>/feature-*` library the way this repo had before converting to React (see the platform repo's CLAUDE.md, "Components live in the app").
- `apps/dashboard-bff` — dashboard's dedicated BFF (port `3004`), which composes MSCA-D's cross-benefit overview by calling `job-bank-bff` and `employment-insurance-bff` over real HTTP (`src/config.ts`'s `JOB_BANK_BFF_URL`/`EMPLOYMENT_INSURANCE_BFF_URL`) — never by importing another domain's in-memory state — plus its own local payments/correspondence data (`src/data.ts`, the same in-memory-stub pattern `job-bank-bff`/`employment-insurance-bff` use for their own domains).
- `libs/data-access` — dashboard's `BenefitOverviewApiClient`/`PaymentHistoryApiClient` interfaces + `Http*` implementations. The one library that stayed separate when this repo's feature libs folded into `apps/dashboard/src/app/`.
- `charts/dashboard` — deploys the frontend+BFF pair as one Helm release, depending on both platform-repo library charts (`mfe-frontend-lib`, `mfe-backend-lib`).

Depends on published packages from GitHub Packages: `@tn4consulting/shared-auth`, `shared-auth-server`, `shared-content-client`, `shared-federation-config`, `shared-federation-runtime`, `shared-i18n`, `shared-locale-sync`, `shared-runtime-config`, `shared-session-cache`, `shared-ui-scds-core` (pinned in `package.json`; keep in sync with `platform-versions.json` in `mfe-pot-platform`). No wrapper package for GCDS/SCDS — `@gcds-core/components` and `shared-ui-scds-core`'s custom elements are consumed directly via JSX, same as every other app.

## Repo-specific things worth knowing

- **`dashboard-bff` is architecturally different from the other two extracted BFFs**: it's a fan-out aggregator for `activeApplications`/`jobApplications`/`eiReportingStatus`, not a self-contained leaf service for those tiles. `overview.ts`'s partial-failure contract (`UpstreamResult<T>` — `{status:'ok', data}` vs `{status:'unavailable'}`) means a slow/failed upstream degrades only its own tile, never the whole response — verified live on `kind` with job-bank/employment-insurance deployed (their tiles returned real data) and separately with one of them killed (only its own tile degraded). `payments`/`correspondence` are served from `dashboard-bff`'s own local `data.ts` (no upstream, so always `'ok'`) — see "Known, accepted tradeoff" note below.
- **In the Helm chart, `JOB_BANK_BFF_URL`/`EMPLOYMENT_INSURANCE_BFF_URL` point at sibling/platform-repo in-cluster Kubernetes Service DNS** (`job-bank-bff.default.svc.cluster.local`, etc.) — genuine cross-Helm-release, cross-repo service-to-service traffic, not routed back out through Ingress. `dashboardBffBaseUrl` on the frontend side is the opposite: `/api`, a same-origin Ingress path rule, since that call is browser-to-server.
- **`strapiBaseUrl` now points at `mfe-pot-platform`'s real `charts/strapi` Ingress hostname** (`http://cms.mfe-pot.local`, browser-to-server, not in-cluster Service DNS — confirmed live).
- **Payments/correspondence used to be served by a separate `client-profile-service` (`mfe-pot-platform`) — removed.** That service had no Helm chart, so its one caller (`dashboard-bff`) 502'd in any real deployment. Its data now lives directly in `dashboard-bff`'s own `src/data.ts`, the same in-memory-stub pattern `job-bank-bff`/`employment-insurance-bff` already use — `HttpPaymentHistoryApiClient` still calls `dashboard-bff`'s `/api/payments`, unchanged, just no longer a proxy. **Known, accepted tradeoff**: `client-profile-service` existed specifically so this data was one shared source across all three domain BFFs (its own doc comment said so); folding it into `dashboard-bff` makes it dashboard-only, narrowing the not-yet-built "tell us once" cross-service demo beat (`../TODO.md`) — flagged there as needing a redesign, not silently dropped.
- **`federation.config.mjs`'s `exposes` map has a second entry beyond the usual `./Component`**: `./PaymentHistoryWidget` (`PaymentHistory.tsx`, exported as `DashboardFeaturePaymentHistory` — that exact name matters, `mfe-pot-shell`'s `routes.tsx` resolves the widget module by it). There's no `./RemoteProviders` entry anymore — `PaymentHistory.tsx` is fully self-configuring (fetches its own runtime config, builds its own `HttpPaymentHistoryApiClient`) whether it's rendered by this app's own `Overview`/`App` or embedded remotely, so there's no host-provided-providers pairing left to carry across the federation boundary. If you ever move or rename `PaymentHistory.tsx`, this is the file that breaks first (`FsPath ... does not exist`), not `tsconfig.app.json`.
- **`Overview.tsx` is both a widget consumer and this app's own composed page** — it renders `WhatsNewList`/`NeedsAttentionList`/`TasksList`/`ConsiderThisList` (this app's own mock/BFF-fed sections) alongside job-bank's job-applications widget and employment-insurance's EI-reporting-status widget, loaded via `useJobApplicationsWidgetLoader()`/`useEiReportingStatusWidgetLoader()` (`shared-federation-runtime`, provided by the shell — see `mfe-pot-shell`'s `routes.tsx`). Both loaders come back `undefined` when there's no shell providing them (standalone serving) — this degrades to the same "unavailable" state a real load failure would show, not a crash, since this app must stay independently testable/serveable with no shell running.
- **`TasksList.tsx` sets `scds-multi-column-list`'s `items`/`columns` imperatively** (`document.createElement` + direct property assignment), not via JSX — those props are non-primitive (arrays), and Stencil never reflects them to/from a DOM attribute at all. See the platform repo's CLAUDE.md "GC Design System" section for the general rule this follows (same pattern as job-bank's `FeatureSearch.tsx`).
- **The payment-history widget's headings/table labels/status text are now CMS-driven** (`dashboard.payment-history.*` keys, batch-fetched via `ContentClient.getPageContents` on mount and re-fetched on cross-remote locale change via `@tn4consulting/shared-i18n`'s `useLocale`) — previously static English mock text. The underlying payment records themselves (`dashboard-bff`'s `data.ts`) are still test data by design; only the surrounding labels moved to CMS. Currency formatting (`$${amount.toFixed(2)}`) is still locale-naive — a narrower, separately-tracked gap (see `../TODO.md`). No component keeps its own hardcoded fallback text anymore — `createContentClient(strapiBaseUrl, assetBaseUrl)` (`content-client.ts`) always wraps Strapi with a `FallbackContentClient` backed by `public/assets/content-fallback/{en,fr}.json`, so a CMS outage degrades to bilingual fallback content instead of English-only text; see the platform repo's CLAUDE.md "i18n" section for the full mechanism.
- **CI** (`.github/workflows/ci.yml`): lint/test/build (including `dashboard-bff`'s separately-run `eslint:lint` target), then builds both images, spins up an ephemeral `kind` cluster, `helm install`s this chart, and curls the Ingress-routed hostname to confirm it serves. The `/api/overview` smoke check deliberately omits the `sub` query param (asserts a 400, not a 404) rather than exercising the real fan-out, since this workflow doesn't also deploy job-bank/employment-insurance. See `README.md` for local install/serve/build/Docker/Helm instructions.
